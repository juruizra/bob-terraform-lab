# Intent-Based Infrastructure Provisioning — Bob Lab

> Provision a production-grade cloud VSI using a single natural-language request to **Bob**.

This lab demonstrates how an AI agent — driven by the `provision-ibm-cloud` skill — can take a plain-English request and produce a fully working, VCS-connected Terraform workspace with real cloud infrastructure at the end.

The workflow is cloud-provider aware: the skill is written for **IBM Cloud** and the `IBM-Cloud/ibm` Terraform provider, but the lab structure, HCP Terraform setup, and VCS patterns apply to any provider.

---

## What you will build

```
Your laptop
  └── live/terraform-ibm-payments-dev/   ← Bob writes Terraform files here
        ├── terraform.tf
        ├── main.tf
        ├── variables.tf
        ├── outputs.tf
        └── .gitignore
              │
              │  git push
              ▼
      GitHub repo (yours)
              │
              │  VCS trigger
              ▼
      HCP Terraform workspace
              │
              │  remote plan + apply
              ▼
      Cloud VPC + VSI with public IP
              ▲
        variable set
        (cloud credentials)
```

By the end of the lab you will have:

- A **private Terraform module** (`vpc-standard`) published in your HCP Terraform private registry
- A **Terraform workspace** connected to your GitHub repo via VCS
- **Cloud credentials managed centrally** as a variable set (`cloud-creds`)
- A running **Ubuntu 22.04 virtual server** with a public floating IP
- A working understanding of the checkpoint-driven provisioning pattern Bob follows

## Running the lab

Open a Bob chat session and type:

```
I need to provision a VSI (ibm-ubuntu-22-04-5-minimal-amd64-19) with a public IP
on IBM Cloud for the payments team.
```

Bob activates the `provision-ibm-cloud` skill and follows the workflow below. Your only job is to answer Bob's questions at the checkpoints.

---

### Workflow overview

| Step | Bob does | You do |
|---|---|---|
| 1 — Org | Lists your HCP Terraform organizations | Confirm which org to use |
| 2 — Modules | Queries your private registry, finds `vpc-standard` | Review |
| 3 — Public registry | Looks up required args for VSI, SSH key, floating IP | Observe |
| 4 — Design checkpoint | Presents full design: module + direct resources + missing info | **Confirm design. Provide:** workspace name, repo, branch, region/zone, SSH key path |
| 5 — Working dir | Finds `live/terraform-ibm-payments-dev/` as the working directory | Confirm |
| 6 — Code + push | Generates `terraform.tf`, `main.tf`, `variables.tf`, `outputs.tf`, `.gitignore`; runs `terraform fmt`; **asks before pushing** | **Approve the push** |
| 7 — Workspace | Creates workspace in HCP Terraform, attaches variable set, adds `ssh_public_key` variable | Observe |
| 8 — README | Generates workspace README | Observe |
| 9 — Plan | Launches `plan_only` run, streams logs | Review plan output |
| 10 — Apply checkpoint | Asks if you want to apply | **Type `yes` to apply** |
| (done) | Reads state outputs, reports `public_ip` and `ssh_command` | Connect to your VSI |

> **Checkpoint pattern:** Bob never pushes to git, creates a workspace, or applies without explicit confirmation from you. Every destructive or external action is gated.

## Known issues and fixes

These are real errors encountered during development of this lab — Bob's skill handles them automatically, but it's useful to understand them.

| Error message | Root cause | Fix |
|---|---|---|
| `Branch doesn't exist` | Workspace created before first commit | Bob now pushes code first, then creates the workspace |
| `invalid target system "IBM"` | Private module source uses uppercase provider | Use `github.com/<owner>/<repo>?ref=vX.Y.Z` as source instead |
| `invalid ref: "1.0.0"` | Git tag is `v1.0.0`, not `1.0.0` | Verify tag with `git ls-remote --tags <repo>` |
| `not authorized to list images` | `IC_API_KEY` lacks VPC permissions | Grant *VPC Infrastructure Services → Viewer* in IBM Cloud IAM |
| `token is malformed` | API key saved with extra whitespace/newline | Update the variable via `tfctl api /vars/<id> -X PATCH` |
| `public key is not of type rsa` | SSH key is `ed25519`, IBM VPC rejects it | Use RSA 4096: `ssh-keygen -t rsa -b 4096` |

## Adapting to another cloud provider

This lab is written for IBM Cloud but the pattern works for any provider:

| What to change | IBM Cloud value | Your value |
|---|---|---|
| Provider in `terraform.tf` | `IBM-Cloud/ibm ~> 1.77` | `hashicorp/aws`, `hashicorp/azurerm`, etc. |
| Credentials variable | `IC_API_KEY` (env var) | `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY`, etc. |
| VPC module | `terraform-ibm-vpc-standard` | Write an equivalent module for your provider |
| Image lookup | `data "ibm_is_image"` | `data "aws_ami"`, `data "azurerm_image"`, etc. |
| VSI resource | `ibm_is_instance` | `aws_instance`, `azurerm_linux_virtual_machine`, etc. |
| Public IP resource | `ibm_is_floating_ip` | `aws_eip`, `azurerm_public_ip`, etc. |
| SSH key resource | `ibm_is_ssh_key` (RSA only) | `aws_key_pair`, `azurerm_ssh_public_key`, etc. |
| Opening prompt | `ibm-ubuntu-22-04-5-minimal-amd64-19` | Your cloud's image name |

The Bob skill (`provision-ibm-cloud`) and the HCP Terraform setup steps are provider-agnostic — only the Terraform resource types and the credential variable names change.

## Key concepts covered

| Concept | Description |
|---|---|
| **Intent-based provisioning** | A single natural-language request drives the full infrastructure lifecycle |
| **Private module registry** | Reusable, company-approved network patterns enforced as code |
| **Variable sets** | Centralized credential management shared across workspaces |
| **VCS-driven workflows** | `git push` is the only deployment trigger — no manual `terraform apply` |
| **Remote execution** | Plan and apply run in HCP Terraform, never on a local machine |
| **Checkpoint pattern** | Bob asks for explicit confirmation before any push, workspace creation, or apply |
